## Requirement understanding

One line: Connect Keeper Secrets Manager (a Conduit plug-in) so Claude, ChatGPT, Cursor, or any MCP-compatible AI gets live, logged access to the secrets stored in a tenant's Keeper vault, with credentials encrypted (https://conduit.wyre.ai/plugins/keeper).

The requester (Ken Lee) wants MSPbots Agent Platform tenants to be able to connect their own Keeper Secrets Manager (KSM) vault as an MCP connector, the same way they already connect Bitwarden, Autotask, HaloPSA, etc. "Live access" means an AI agent can call tools that read (and, per a secrets manager's normal purpose, write) the secrets a tenant stores in Keeper, scoped to whatever that tenant's own Keeper account can see. "Credentials encrypted and every action logged" describes the platform's existing per-connector behaviour (encrypted-at-rest credential storage and an audit log), not something this repo has to build itself — see Non-goals.

## Product design

### Goals / Non-goals

**Goals**
- Give an Agent Platform tenant's AI agents live, per-request access to the secrets, fields, and folders in that tenant's own Keeper vault, through a small set of MCP tools (list, get a single field, create, update, delete), using the tenant's own already-bound KSM configuration — no server-side persistence of any tenant's secrets or credentials.
- Fit the existing "Credential form" connect shape the platform already uses for this class of vendor (static, reusable credential; see Current state) — this ticket does not add a new connect-dialog shape.

**Non-goals**
- **Encrypting credentials at rest and logging every tool call for audit.** That is the Agent Platform/gateway's existing behaviour (`ProductDocs/15-Capabilities.md`: *"They're stored encrypted for your tenant and injected on every MCP request"*; connector-wide audit log is a platform feature already used by every other connector, including the sibling `bitwarden-mcp`). This repo does not re-implement storage encryption or an audit trail — it only avoids making those platform guarantees harder to keep (no secrets in logs, no secrets on disk — see Non-functional).
- **Folder structure management** (create/update/delete folder). The ticket's one-line ask is "live access to the secrets," not vault structure administration; see Decisions made by DEV01 for why this is deferred rather than refused.
- **File/attachment upload and download on a secret.** MCP tool results are JSON/text; piping binary attachments through that channel has no concrete ask behind it in this ticket.
- **TOTP code generation.** A niche capability of the SDK, not named in the ticket.
- **Any OAuth flow.** KSM is a "normal vendor" (SOP §A3's category) — a single static, Header-carried credential blob — so there is nothing to design beyond the Credential form MSPbots already has.
- **Changing the Agent Platform's generic "Connect <Name>" UI.** Out of scope for an MCP connector repo; the existing Credential form shape already fits (see Current state).

### Acceptance criteria AC1..AC9

- **AC1**: Given a tenant has supplied a valid bound KSM config (base64) in the `X-Keeper-Config` header, When the agent calls `keeper_list_secrets`, Then the tool returns at most `limit` (default 50, hard cap 200) secrets (uid/title/folder_uid/type only, not full field values), and `has_more` is `true` if more exist.
- **AC2**: Given a request omits the `X-Keeper-Config` header, When any tool is called, Then the service returns `401` listing the required header, and makes no outbound call to Keeper.
- **AC3**: Given a valid config and a record UID that exists, When the agent calls `keeper_get_secret` with that UID, Then the tool returns the record's type, title, and full field list (values included — returning the secret value is this service's entire purpose, so values are never masked by this layer).
- **AC4**: Given a record UID the bound config cannot see (unknown, or belongs to a different vault), When the agent calls `keeper_get_secret`, Then the tool returns the structured `not_found` error — not a 500, and not an empty success.
- **AC5**: Given a valid `folder_uid` and field values, When the agent calls `keeper_create_secret`, Then a new record is created and its UID is returned; Given a `folder_uid` that does not exist, Then the tool returns `invalid_argument` naming the bad field.
- **AC6**: Given one or more explicit, existing record UIDs, When the agent calls `keeper_delete_secret`, Then exactly those records are deleted and the tool reports how many; the tool never accepts a "delete everything in folder X" / vault-wide request — only an explicit UID list.
- **AC7** (permission & multi-tenant, must be answered explicitly): Given two concurrent requests from two different tenants (two different `X-Keeper-Config` values) arrive at the same running service instance, When both are processed, Then neither request's secrets, folder data, or credentials are visible to the other. This repo adds no MSPbots-side tenant table of its own — isolation is enforced entirely by (a) which Keeper account a given config is bound to, upstream, and (b) this service's per-request credential handling never sharing state across requests (contextvars, reset after every response). There is no cross-tenant data path inside this service to guard against beyond that.
- **AC8**: Given the upstream Keeper API returns a transient rate-limit or 5xx response, When a tool call is in flight, Then the service retries with bounded backoff within the per-call timeout budget and, if still failing, returns a structured `rate_limited` or `upstream_error` envelope rather than hanging or raising an unhandled exception.
- **AC9**: Given a config bound to one real Keeper account, When used for any tool call, Then only the records and folders visible to that Keeper account are ever returned — confirmed end to end with two real accounts (TC11, needs a real vendor account; not blocking delivery per the SOP's "no test account is not a blocker" rule).

## Tech design

### Conclusion

Build `keeper-mcp` as a stateless Python 3.12 + uv + FastMCP service — the same stack as the org's other vendor MCP repos (`bitwarden-mcp`) — following the `vendor-mcp-development` SOP's "main line A" (first version of a new MCP service), since the repo is a zero-code scaffold. The core mechanism: for every tool call, construct a `keeper_secrets_manager_core.SecretsManager` client from `InMemoryKeyValueStorage(config=<base64 blob read from the X-Keeper-Config header>)`, never touching disk and never caching anything across requests. This is the cheapest design that satisfies the SOP's three "operating model" laws (credentials only from a Header, request-level isolation, true statelessness) because Keeper's own documentation confirms the bound config — not the one-time token — is the stable, reusable, concurrency-safe credential (Current state, "Configuration stability"). No bootstrap, no server-side binding step, no token exchange per call: the tenant does the one-time redemption themselves, once, outside this service, exactly like they would for any other static-credential connector.

### Where the current implementation lives

`keeper-mcp@main` (03543c6) has only `README.md:1-2` — nothing to extend; this is a from-scratch build. Nearest sibling for shape: `bitwarden-mcp@main` (5819c3c) — `src/bitwarden_mcp/server.py`, `config.py`, `api_client.py`, `tools/{groups,members}.py`; README structure `Authentication` / `Claude Desktop Setup` / `Transport Modes` / `Tool List` / `Test Examples` / `API Reference` / `Known Limitations` (`bitwarden-mcp@main README.md:1-275`). The new repo should mirror this file layout and README structure rather than invent a different one.

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| A | Wrap Keeper's official `keeper-secrets-manager-core` Python SDK; build a fresh `SecretsManager` per request via `InMemoryKeyValueStorage` | Reuses vendor-maintained crypto/signing/record-parsing code; the SDK's own docs confirm this exact usage is concurrency-safe | Adds one dependency (Apache-2.0, actively maintained by Keeper) | **Chosen** |
| B | Call Keeper's REST endpoints directly and re-implement the KSM request-signing protocol (ECDH key derivation, per-request signing) ourselves | No SDK dependency | Re-implementing a vendor's crypto/signing protocol is exactly the "build it ourselves" path the SOP says to avoid when a maintained library exists; materially higher risk of a subtle signing bug | Rejected — no reason to not reuse a maintained official SDK |
| C | Have this service redeem the tenant's one-time token itself and cache the resulting bound config server-side | Mirrors how OAuth-style connectors behave | Directly violates "no persisted tenant secrets / true statelessness"; the one-time token can only be redeemed once, so this breaks on a process restart or any horizontal scale-out (two instances can't both redeem it) | Rejected |

### Reuse & cleanup

- **Reuse**: official `keeper-secrets-manager-core` PyPI package (Apache-2.0) for all crypto/signing/record parsing — do not hand-roll KSM's protocol. FastMCP framework and the Header-credential + `contextvars` isolation pattern are already proven in this org by `bitwarden-mcp` (`config.py`/middleware shape); follow the same pattern rather than inventing a new one.
- **New dependency**: `keeper-secrets-manager-core` (pin a version in `pyproject.toml`/`uv.lock`) — replaces having to re-implement Keeper's ECDH-based request signing and record encryption, which the SOP's reuse-before-build-before-buy ordering requires avoiding when a maintained vendor SDK exists.
- **Interfaces**: tool parameters are generic and composable — e.g. `keeper_create_secret(folder_uid: str, title: str, record_type: str = "login", fields: dict[str, Any])` rather than one positional parameter per possible Keeper field — so a future record type doesn't require a new tool signature.
- **In-scope cleanup**: none. The repo has no prior code (empty scaffold); there is nothing to clean up in this unit.
- **Suggested follow-ups** (not in this unit): folder create/update/delete tools, file-attachment tools, a TOTP tool — all explicitly deferred below in Decisions made by DEV01, with the reasoning for deferring rather than building them now.

### Data & API contract

- **Transport**: `POST /mcp` (Streamable HTTP, JSON-RPC 2.0); `GET /health` (`{"status":"ok"}`, no upstream dependency).
- **Credential header**: `X-Keeper-Config` (string, required) — base64-encoded KSM bound configuration JSON (`clientId`/`privateKey`/`appKey`/`hostname`/etc.), produced once by the tenant redeeming their own One-Time Access Token via Keeper's own tooling — **never a one-time token itself** (see Decisions made by DEV01). Missing header → `401 {"error":"Missing credentials","required_headers":["X-Keeper-Config"]}`.
- No other required headers: unlike Bitwarden's region-specific URL overrides, KSM's hostname is already embedded in the bound config blob (`docs.keeper.io`, "Configuration stability" above), so there is nothing else to pass per request.
- **Tools** (`tools/call` `params.arguments` → result, compact JSON, `ensure_ascii=False`, no `indent=2`):
  - `keeper_list_secrets(folder_uid?: str, title_contains?: str, limit?: int = 50, offset?: int = 0) -> {"secrets": [{"uid","title","folder_uid","type"}, ...], "has_more": bool}` — `limit` capped server-side at 200; the vendor SDK has no native pagination, so this service slices the full `get_secrets()` result.
  - `keeper_get_secret(uid: str) -> {"uid","title","type","fields": [{"type","label","value"}, ...]}` — `not_found` if the config cannot see this UID.
  - `keeper_get_secret_field(notation: str) -> {"value": <any>}` — `notation` is Keeper Notation syntax (`UID/field/password`, `UID/custom_field/<label>`) passed straight to the SDK's `get_notation`.
  - `keeper_list_folders() -> {"folders": [{"uid","name","parent_uid"}, ...]}`.
  - `keeper_create_secret(folder_uid: str, title: str, record_type: str = "login", fields: dict[str, Any]) -> {"uid": str}` — `invalid_argument` naming the bad field/folder.
  - `keeper_update_secret(uid: str, fields: dict[str, Any]) -> {"uid": str, "updated_fields": [str, ...]}` — partial update, only named fields change.
  - `keeper_delete_secret(uids: list[str]) -> {"deleted": [str, ...], "not_found": [str, ...]}` — no folder-wide or vault-wide variant exists in the schema (AC6, TC8).
- **Error envelope** (SOP §4 vocabulary): `{"error": {"code","message","retryable"}}`, `code ∈ {not_configured, unauthorized, not_found, invalid_argument, rate_limited, upstream_error}`. Tools never raise; they return this envelope as the tool result.
- **DB**: none — the service has no database and no migration.
- **Backward compatibility**: n/a for v1 (first version). Any future breaking change (renaming/removing a tool, dropping a required param, tightening an enum, renaming the credential header) must follow SOP §13 — advance notice, no silent release.

### Non-functional

- **Idempotency & concurrency**: every tool call builds a fresh SDK client from that request's own header value (`contextvars`, no module-level singleton, no shared HTTP session across tenants). The concurrency-safety of reusing one bound config is a documented upstream property (Current state, "Configuration stability"), so this service adds no locking of its own.
- **Performance**: the upstream SDK has no native list pagination (`get_secrets()` returns the whole vault's records); `keeper_list_secrets` slices that result to `limit`/`offset` in this service. A tenant with a very large vault means a possibly large single upstream fetch per list call — flagged as a known limitation, not verified against a real large vault since no test account is available (see Risks).
- **Security**: credentials exist only in the request header and that single request's contextvar lifetime; never logged (log statements must redact the header value and any field whose label looks like password/secret); never written to disk. `gitleaks detect` run before delivery per SOP §11.
- **Multi-tenant isolation**: enforced entirely by which Keeper account a given `X-Keeper-Config` is bound to — there is no service-side tenant table to get wrong (AC7/AC9).
- **Observability**: log tool name, outcome (ok / error code), and latency only — never secret values, never the header value, never field contents.

## Decisions made by DEV01

(No one was available to ask; each of these is a small, reversible choice made for this first version, written down so it can be revisited.)

- **Single credential header `X-Keeper-Config` carrying the bound base64 config — not a one-time token, not split into per-field headers.** Why: Keeper's own docs confirm the bound config (not the one-time token) is the stable, reusable, concurrency-safe credential; splitting one atomic blob into multiple headers (`clientId`/`privateKey`/`appKey`/`hostname`) adds surface for partial/mismatched updates with no benefit, since the SDK already treats it as one unit. Alternative considered: per-field headers mirroring `bitwarden-mcp`'s two-header pattern — rejected because Bitwarden's two values are exchanged fresh on every call, whereas Keeper's four-plus values are only ever used together as one bound unit.
- **No folder create/update/delete tools in v1.** Why: the ticket's one-line ask is "live access to the secrets," not vault-structure administration; folder mutation is less common and has no concrete requirement behind it in this ticket. Alternative: include for completeness — rejected to keep the tool count and blast radius minimal for a first version; can be added as a fast follow if a tenant asks.
- **No TOTP tool, no file-attachment tools in v1.** Why: niche SDK capabilities, not named in the ticket; attachments would require base64-inflating binary payloads through a JSON-RPC text channel with no concrete use case behind it. Alternative: include for parity with the SDK's full surface — rejected; SOP §A4 says tools are "capabilities," not an API-endpoint mirror.
- **Client-side pagination (limit/offset slicing of the full `get_secrets()` result) rather than no cap at all.** Why: SOP §A4 requires `list` tools to cap output (≤200 hard limit) and avoid unbounded responses; the vendor SDK itself has no native page cursor, so the cap has to live in this service.
- **Write tools accept only explicit resource IDs, never folder-wide or vault-wide bulk operations.** Why: SOP §A4's rule against accepting vague batch deletes — a `keeper_delete_secret` that accepted "everything in folder X" would be one bad agent turn away from wiping a tenant's vault.

To change any of these, say so in a comment and move the ticket back to 5b - ready for groom.
